MaudeSignal connector API

MaudeSignal cuts the time to investigate a complaint against FDA data and to prepare PMS evidence, and keeps every fact traceable for audit.

MaudeSignal reads FDA MAUDE adverse-event reports, recalls and 510(k) records for AI-enabled medical devices and flags what changed. This API gives a Meta Muse custom connector six read-only tools over that data. Every answer is a short summary that can be read aloud, a list of facts that each carry an openFDA or record link, a fixed advisory line, and where the data came from.

The six tools

All are read-only. Send your key in the X-API-Key header. Never put it in the URL: a request with a key-like query parameter is refused with 400.

ToolRequestInputWhat you get
what_changed_this_weekGET /v1/tools/what_changed_this_weekproduct_code (optional, 3 letters, e.g. LLZ)The latest stored week from the demo snapshot, with its dates. A code outside the stored set is checked live on openFDA.
check_device_typeGET /v1/tools/check_device_typeproduct_code (3 letters)Live openFDA report counts for any device type, using the same four rules, windows and thresholds as the weekly detector. If openFDA cannot be reached for a stored code, the stored snapshot answers and says so.
lookup_deviceGET /v1/tools/lookup_deviceany of device_name, model, manufacturer, k_number, udi, gtin, product_code (at least one)For what a model read from a device photo: up to 3 possible FDA records from openFDA (510(k), registration & listing, UDI), each with why_matched and why_not_matched and its links, plus this week's change, recent recalls and the report count for the top product code. status is needs_person_to_confirm, no_match_found or search_failed; confirmed is always null: a person confirms one record, or none. No model call.
askPOST /v1/tools/ask (body: {"question": "..."}, 3 to 500 characters)questionA Muse Spark answer built only from stored records. Each sentence goes through the claim gate. Sentences the gate did not verify are listed under withheld and are never in speakable. Without a model key, or after the cost cap, the closest recorded answer is returned and labelled recorded. POST only because the question travels in the body; nothing is written.
get_reportGET /v1/tools/get_reportreport_id (MAUDE report id)Key fields and the start of the narrative of one stored report, with its record link.

Prompts and server instructions

Over MCP the server also offers three prompts (prompts/list, prompts/get; also listed by GET /v1/connect). Each returns one message that asks the model to call the tools above. Each message says: cite the FDA links, this is not medical advice, and say "recorded" for recorded answers.

PromptArgumentsWhat it asks the model to do
morning_briefproduct_codes (comma-separated, up to 10)Call what_changed_this_week for each code and summarise with links.
check_this_devicetext (name, model, maker, K-number or UDI, read from a photo or typed)Call lookup_device, list up to 3 possible matches with why, and ask the person to confirm one before going further.
does_this_apply_to_usproduct_code; our_device_description (optional)Call check_device_type, what_changed_this_week and recalls and show the problem patterns as questions for the person's own records, never as a verdict.

The MCP initialize reply carries these instructions, and the OpenAPI description starts with the same text: always cite the FDA links in each answer; not medical advice and nothing is filed with FDA; confirm the product code with the person before guessing one (use lookup_device or ask); say "recorded" and the date for a recorded answer; never present withheld sentences as fact; a person confirms every device match; web results are not FDA records.

Error format

A refused input gets HTTP 422 (REST) or isError: true (MCP) with a short message that says what to fix. An empty body, a body that cannot be parsed as JSON or one sent without a JSON content type gets "The request body is not valid JSON."; valid JSON that is not an object (such as [1, 2]) gets "The request body must be a JSON object."; a wrong field is named. The JSON body is always {"error": {"code": "...", "message": "..."}}, plus "suggestions": [...] when there is something to offer.

  • A product code that is not three letters: "A product code is three letters, for example LLZ or QIH."
  • A three-letter code with no stored data, no reports on openFDA and no entry in the openFDA device classification list (unknown_product_code): "QAH isn't a product code we know - did you mean QAQ, QAS or QIH?", with up to 3 known codes one edit away in suggestions. When no known code is one edit away, the message is just "ZZZ isn't a product code we know." with no suggestions. The message repeats the code you sent (only a three-letter code that passed the letters check). Suggestions are never applied automatically, and a code with stored data, openFDA reports or a classification entry is never corrected (one with only a classification entry is answered "openFDA returned no reports"). If the classification list cannot be reached, the code is not called unknown. recalls never fails on an unknown code: it keeps its "no recalls on file" answer, may check openFDA to confirm the code exists, and returns the suggestions in the answer's suggestions list.
  • A malformed K-number: "K-numbers look like K123456 (the letter K and six digits)."
  • A UDI or GTIN whose last digit fails the GS1 check: the message says so.
  • A missing input is named ("product_code is required."); a question outside 3 to 500 characters gets the limit.

Authentication

Header name: X-API-Key. Keys are created by the operator (see the deploy notes) and are read-only. A missing or wrong key gets 401 with the same body either way. Repeated wrong keys from one address get 429. The key is never written to a response, a log or the audit log; the audit log names a caller by a server-side keyed hash of the key (an HMAC under the operator's pepper, 12 hex characters), never the key or its digest.

Data provenance

Every answer says where it came from. stored_demo_snapshot: the committed demo copy of openFDA data, with the date it was fetched; not live. live_openfda: counts fetched at the UTC time in queried_at_utc. recorded_answer: a real, gated earlier run of the copilot. live_model: a Muse Spark answer from this call. MHRA (UK) alerts, where present, are regulator context only and never counted in a MAUDE number.
